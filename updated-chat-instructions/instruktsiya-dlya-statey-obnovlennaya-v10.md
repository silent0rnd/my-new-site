# Инструкция для SEO-статей naklikay.ru (версия 10)

## 1. Назначение

Этот файл определяет общие правила содержания всех SEO-статей naklikay.ru.

Цель статьи:

- полностью решить задачу человека;
- получать релевантный органический трафик из Яндекса и Google;
- быть пригодной для использования и цитирования в генеративных ответах нейросетей;
- давать оригинальную практическую ценность;
- быть удобной для чтения и извлечения прямых ответов;
- сохранять стиль автора.

Главный принцип: сначала поисковый интент и польза человеку. Классическое SEO и GEO применяются как два дополняющих друг друга слоя оптимизации. Нельзя ухудшать полезность и естественность текста ради ключей, формального SEO или попыток специально угодить нейросетям.

Процесс создания изображений и архива находится в актуальном файле `instruktsiya-illyustratsii-v7.md`. Внешний вид изображений находится только в `Дизайн-система-изображений-оптимизированная.md`.

## 2. Тип материала

Перед исследованием определить тип:

- `STANDARD` - обычная информационная, коммерческая или смешанная SEO-статья;
- `FORECAST` - статья-инструкция, статья-прогноз, продвижение конкретной ниши или материал с расчётом рекламной экономики.

Для `FORECAST` дополнительно применять `instruktsiya-statya-prognoz-v17.md`.

## 3. Входные данные

Использовать переданные пользователем:

- тему;
- основные и дополнительные запросы;
- географию;
- аудиторию;
- задачу статьи;
- экспертные мысли;
- реальные кейсы, цифры и ограничения.

Если критически важного значения нет и его нельзя установить исследованием, запросить только это значение. Не приписывать пользователю данные, опыт или результаты, которых он не сообщал.

## 4. Исследование

Перед написанием:

1. Определить основной запрос, поисковый интент и главный вопрос, на который статья должна ответить сразу.
2. Определить связанные вопросы, сущности, естественные словоформы и отдельные смысловые вопросы, для которых нужны самостоятельные прямые ответы.
3. Изучить актуальную выдачу Яндекса и Google.
4. Посмотреть сильные страницы из топа и определить:
   - какие задачи они решают;
   - какие сведения повторяются;
   - чего не хватает;
   - какие данные устарели;
   - какую дополнительную практическую ценность можно дать.
5. Проверить изменяемые факты по первичным или официальным источникам.
6. Для продуктов Яндекса отдавать приоритет официальной документации Яндекса.
7. Найти на naklikay.ru только реально подходящие статьи, кейсы и коммерческие страницы.
8. Учесть экспертные мысли пользователя.

Не копировать структуру конкурентов и не собирать статью пересказом нескольких страниц.

## 4.1. Доработка уже опубликованной страницы

Этот режим использовать, когда пользователь просит усилить, обновить или доработать существующую страницу для роста в поиске.

Главный принцип: не переписывать сильную страницу целиком без причины. Сначала определить конкретные точки роста по фактическим данным Яндекса, затем менять только то, что связано с обнаруженным разрывом.

### 4.1.1. Анализировать URL по всему значимому набору запросов

Не ограничиваться одним основным запросом страницы.

Перед рекомендациями:

1. Взять все значимые запросы, по которым текущий URL уже получает показы в Яндексе.
2. Для каждого запроса учитывать по возможности:
   - показы;
   - клики;
   - CTR;
   - среднюю позицию;
   - динамику относительно предыдущего периода.
3. Разделить запросы минимум на группы:
   - топ-3;
   - позиции 4-10;
   - позиции 11-20;
   - ниже 20.
4. Приоритетно искать точки роста среди запросов с заметными показами на позициях 4-10 и 11-20.
5. Не считать случайный запрос с единичными показами самостоятельным направлением оптимизации без дополнительных оснований.

Доработка страницы должна учитывать весь реальный поисковый кластер URL. Нельзя усиливать один запрос так, чтобы без необходимости ухудшить соответствие другим важным запросам, по которым страница уже получает трафик или находится близко к топу.

### 4.1.2. Обязательная проверка каннибализации

Для основных и приоритетных запросов страницы проверить, получает ли заметные показы по тем же запросам другой URL naklikay.ru.

Если по одному запросу видны несколько URL:

1. Определить, действительно ли страницы закрывают один и тот же интент.
2. Не считать единичные или случайные показы доказанной каннибализацией.
3. Если интенты разные, точнее развести страницы по смыслу, структуре, Title, H1, внутренним ссылкам и содержанию.
4. Если интент фактически один, определить основной URL и рассмотреть:
   - усиление основного URL;
   - изменение внутренней перелинковки;
   - перенос полезного содержания;
   - объединение страниц, если это действительно оправдано.
5. Не объединять и не удалять страницы автоматически только из-за пересечения нескольких запросов.

Проверка каннибализации является обязательным этапом перед серьёзной доработкой страницы.

### 4.1.3. Анализировать актуальный топ Яндекса по приоритетным запросам

Перед изменением опубликованной страницы изучить текущую выдачу Яндекса по тем запросам, которые являются реальными точками роста.

Сравнивать не только наличие тем у конкурентов, а конкретный разрыв между нашей страницей и страницами, которые находятся выше:

- поисковый интент;
- тип страницы;
- прямота ответа;
- структура H1/H2/H3;
- полнота раскрытия конкретного вопроса;
- формат ответа;
- таблицы;
- расчёты;
- примеры;
- практические детали;
- коммерческая составляющая;
- Title;
- фактический сниппет в выдаче;
- дополнительные элементы, которые реально помогают закрыть интент.

Не копировать структуру топа механически.

После анализа сформулировать конкретную причину изменения. Например:

- недостаточно прямой ответ в начале;
- отсутствует важный самостоятельный интент;
- слабая сравнительная таблица;
- недостаточно практического примера;
- коммерческий запрос раскрыт как чисто информационный;
- Title хуже соответствует интенту;
- сниппет плохо объясняет пользу страницы.

Менять только те элементы, для которых найден реальный разрыв или другая обоснованная причина.

### 4.1.4. Отдельно анализировать CTR и сниппет

Если страница уже находится на хороших позициях, но получает слабый CTR, не начинать автоматически с переписывания основного текста.

Сначала проверить:

- фактический Title в выдаче;
- фактическое описание сниппета;
- насколько сниппет соответствует запросу;
- понятна ли польза страницы;
- нет ли разрыва между запросом и обещанием в сниппете;
- можно ли улучшить Title, meta description или первые смысловые фрагменты страницы.

Особенно осторожно работать со страницами и запросами, уже находящимися в топ-3. Без конкретной проблемы не делать крупную переработку сильного URL.

### 4.1.5. После доработки проверить внутреннюю перелинковку

После изменения целевой страницы проверить, какие существующие страницы naklikay.ru тематически связаны с ней и могут естественно ссылаться на неё.

При необходимости добавить релевантные внутренние ссылки.

Правила:

- ссылка должна помогать пользователю продолжить тему;
- анкор должен быть естественным и соответствовать контексту;
- не ставить одинаковый точный анкор массово;
- не добавлять ссылки только ради количества;
- не создавать искусственные блоки перелинковки, если ссылка уместна внутри текста;
- при каннибализации использовать перелинковку для более ясного обозначения основного URL.

### 4.1.6. Принцип минимально необходимого изменения

Для существующей страницы сначала определить, что уже работает хорошо, и сохранить это.

Не переписывать материал целиком, если проблему можно решить изменением:

- первого ответа;
- одного H2;
- отдельного смыслового блока;
- таблицы;
- Title или description;
- внутренней перелинковки;
- конкретного примера;
- структуры одного раздела.

После существенной доработки учитывать дату изменения и существующий журнал SEO-изменений. Не делать новую крупную переработку только потому, что результат не изменился сразу, если ещё недостаточно данных для оценки предыдущей правки.

## 5. Факты и источники

Нельзя придумывать:

- статистику;
- исследования;
- цены;
- результаты;
- кейсы;
- функциональность сервисов;
- цитаты;
- личный опыт автора;
- средние показатели рынка.

Каждую изменяемую цифру проверить до написания. Отдельный журнал источников пользователю не выводить.

Во внешнем тексте статьи:

- не добавлять внешние ссылки;
- не добавлять повторяющиеся блоки `Источник`;
- разрешена краткая атрибуция, например `по данным Яндекса за август 2026 года`;
- если надёжных данных нет, прямо указать ограничение и не заполнять пробел догадкой.

Ссылки в статье могут вести только на проверенные страницы naklikay.ru. URL нельзя придумывать.

## 6. Интент и структура

Статья строится по принципу `answer-first`.

Сразу после H1 дать прямой ответ на основной запрос. Обычно достаточно 1-3 коротких абзацев. В них нужно сообщить главное решение, вывод или порядок действий без исторического вступления, общих рассуждений и длинного разгона. Если ответ зависит от важного условия или ограничения, назвать его сразу.

Каждый ключевой H2 должен быть самостоятельным смысловым блоком. Если заголовок отвечает на вопрос, сравнивает варианты или объясняет действие, первые 1-3 предложения под ним должны сразу давать ответ по существу. После этого раскрывать причины, условия, примеры, расчёты, ошибки и детали.

Каждый раздел должен выполнять понятную функцию: отвечать, объяснять, сравнивать, показывать расчёт, давать инструкцию или помогать принять решение.

Использовать:

- ровно один H1;
- самостоятельные H2;
- H3 только при реальной необходимости;
- короткое вступление с прямым ответом;
- небольшие абзацы;
- списки, таблицы и формулы только когда они упрощают понимание.

Не начинать статью с истории вопроса, определения очевидных терминов, общих фраз о важности темы или описания того, что будет рассмотрено далее, если этого не требует интент.

FAQ добавлять только для реальных дополнительных вопросов, не раскрытых выше. Не превращать статью в набор искусственных вопросов и ответов ради GEO.

Фиксированной нормы объёма нет. Удалять воду, повторы, очевидные рассуждения, искусственные вступления и разделы без практической функции.

## 7. Коммерческий интент

Если запрос коммерческий или полукоммерческий, уместно раскрыть:

- понятный оффер;
- условия или ориентир по стоимости, если он подтверждён;
- состав работы;
- релевантные кейсы;
- естественный CTA;
- ссылки на подходящие страницы сайта.

Не превращать информационную статью в рекламный лендинг, если интент этого не требует.

## 8. SEO-META

`seo_title`, H1 и `meta_description` создавать индивидуально под интент и содержание статьи.

Шаблонные формулы использовать только как запасной вариант. Не делать серию заголовков, в которых меняется только название ниши.

### seo_title

- информативно описывает страницу;
- естественно содержит основной запрос или близкую формулировку;
- не содержит перечня ключей и повторов;
- отличается от H1, если это улучшает понятность и кликабельность.

### meta_description

- кратко объясняет пользу материала;
- отражает фактическое содержание страницы;
- не копирует `seo_title`;
- не содержит переспама и рекламных штампов.

### slug

- короткий;
- понятный;
- латиницей;
- соответствует теме;
- без дат и слов, которых нет в статье, если дата не является частью интента.

## 9. Ключевые запросы

Основной запрос или близкую формулировку желательно естественно использовать в `seo_title`, H1 и начале статьи.

Дальше использовать словоформы, синонимы, связанные термины и тематические сущности.

Запрещены:

- искусственная плотность ключей;
- повтор точного запроса ради SEO;
- SEO-абзацы без пользы;
- переспам географией;
- скрытый текст;
- неестественные вхождения.

## 10. Авторская ценность

Статья должна содержать хотя бы один подтверждённый элемент, которого нет в типовом пересказе выдачи:

- экспертный вывод пользователя;
- прозрачную методику расчёта;
- практическое ограничение;
- разбор ошибки;
- собственный кейс или данные, если пользователь их предоставил;
- полезное сравнение вариантов.

Не писать от первого лица о действиях и результатах, которых пользователь не подтверждал.

Автор - Максим Мирошников, специалист по платному трафику и Яндекс Директу. Писать живым русским языком, конкретно, без канцелярита и искусственной экспертности.

Не использовать в `ARTICLE-BODY` цепочки из отдельных слов или коротких фраз, соединённых стрелочными символами. Такая подача выглядит технической и не соответствует естественному авторскому тексту. Последовательность этапов описывать обычным предложением или, если этапы нужно явно разделить, маркированным или нумерованным списком. Стрелочные символы в публикуемом тексте не использовать.

Не использовать длинное тире. Использовать дефис `-`.

## 11. GEO / AI-friendly структура

GEO здесь означает оптимизацию материала для генеративных ответов нейросетей. Она не заменяет классическое SEO и не требует специальных трюков. Задача - сделать важные фрагменты статьи понятными, точными и самодостаточными.

### Прямые ответы

Для основного запроса и ключевых вопросов:

- сначала дать короткий прямой ответ;
- затем раскрыть условия, причины, ограничения и детали;
- важный вывод не прятать в середине длинного раздела;
- если возможен однозначный ответ, сформулировать его прямо.

### Самодостаточные смысловые блоки

Ключевой абзац или небольшой блок должен быть понятен без обязательного чтения нескольких предыдущих разделов.

Предпочитать конкретные формулировки:

- называть предмет, сервис, настройку или показатель явно;
- не злоупотреблять словами `это`, `такой`, `данный`, `он`, если без соседнего абзаца непонятно, о чём речь;
- указывать важные условия рядом с выводом;
- рядом с числом указывать, что именно измеряется, период, географию или другие критичные условия, если они влияют на смысл.

Не нужно механически повторять название темы в каждом абзаце. Самодостаточность не должна превращаться в переспам.

### Цитируемые фрагменты

По возможности формулировать важную информацию так, чтобы отдельный фрагмент можно было корректно использовать как готовый ответ:

- определения;
- краткие инструкции;
- условия применения;
- ограничения;
- формулы;
- числовые ориентиры;
- экспертные выводы;
- причины ошибок;
- сравнение вариантов.

Сначала формулировать вывод, затем доказательство или объяснение.

### Факты, расчёты и прогнозы

Чётко разделять:

- подтверждённый факт;
- расчёт автора;
- прогноз;
- экспертный вывод или практическую рекомендацию.

Для изменяемых фактов и цифр при необходимости указывать в тексте источник, период и контекст, например `по данным Яндекса за август 2026 года`. Не перегружать статью формальными ссылками и повторяющимися блоками источников.

### Структура для генеративных систем

Использовать самостоятельные и понятные H2. Заголовок должен позволять определить тему раздела без чтения всего текста.

Предпочитать:

- короткий ответ в начале раздела;
- конкретные существительные вместо неопределённых ссылок;
- ясные причинно-следственные связи;
- перечисления для последовательностей и условий;
- таблицы только для реального сравнения;
- точные числа с единицами измерения;
- явные ограничения и исключения.

Не нужно:

- дробить статью на десятки микроблоков;
- создавать искусственные FAQ;
- повторять один и тот же ответ разными словами;
- писать отдельные SEO-абзацы для нейросетей;
- увеличивать объём ради полноты;
- жертвовать естественным языком ради предполагаемых GEO-факторов.

Глубина статьи сохраняется: прямой короткий ответ открывает тему, а последующий текст даёт доказательства, механику, примеры и практические детали.

## 12. Данные и иллюстрации

Любой факт, число, формула или вывод, показанный на иллюстрации, должен уже присутствовать обычным текстом в `ARTICLE-BODY`.

Иллюстрация дополняет текст, но не заменяет индексируемое объяснение.

Alt должен естественно описывать изображение и его смысл в разделе. Не использовать alt как список ключей.

Для каждой иллюстрации в `IMAGE-SPECS` обязательно указывать отдельное поле `Подпись` с готовым текстом видимой подписи под изображением (`figcaption`). Подпись должна кратко пояснять главную мысль или практический смысл картинки, соответствовать разделу статьи и не дублировать Alt дословно. Не придумывать в подписи новых фактов, чисел и результатов. Подпись предназначена для отображения под картинкой на странице, а не для размещения внутри самого изображения.

### Выбор количества иллюстраций

Для каждой статьи создавать **не менее трёх** иллюстраций. Верхнего фиксированного лимита нет: итоговое количество автор определяет самостоятельно после написания полного `ARTICLE-BODY`, исходя из темы, объёма, структуры и конкретной пользы для читателя. Для большой или насыщенной практическими деталями статьи уместно больше трёх изображений. Не ограничиваться тремя по привычке, но и не добавлять изображения ради количества.

Перед формированием `IMAGE-SPECS` обязательно выполнить смысловой обзор всей статьи:

1. Пройти по разделам H2/H3 и найти места, где визуальное объяснение поможет понять материал быстрее, чем дополнительный абзац.
2. Выделить самостоятельные сюжеты: процесс, причинно-следственную связь, сравнение, расчёт, устройство, пример, интерфейсную логику или предметную сцену.
3. Для каждого кандидата сформулировать конкретную главную мысль и ответить, что человек поймёт благодаря изображению. Если картинка лишь украшает статью или повторяет соседнее изображение, исключить её.
4. Выбрать все оправданные сюжеты, сохранив минимум три изображения. Количество определяется по результатам обзора, а не по количеству слов, H2 или условному интервалу между картинками.
5. Отдельно проверить, нет ли в статье важных сложных разделов, которые выиграют от дополнительной визуализации. При наличии таких разделов добавить задания сверх трёх.

Иллюстрации должны удерживать внимание за счёт пользы и выразительности, а не плотности картинок как таковой. Увеличение их количества само по себе не гарантирует рост времени на странице или SEO-позиций.

### Размещение иллюстраций

Место каждой иллюстрации определить уже на этапе создания `IMAGE-SPECS`. Картинка должна стоять рядом с тем фрагментом статьи, который она объясняет или визуально дополняет.

Обязательные правила:

- каждая картинка раскрывает самостоятельную мысль, связанную с конкретным смысловым фрагментом статьи;
- не назначать две картинки в одну точку, не размещать их подряд или непосредственно после одного и того же блока;
- распределять изображения естественно по ходу чтения, не оставлять крупные содержательные части статьи без иллюстраций, если там есть подходящие сюжеты;
- смысловая связь важнее механической равномерности: нельзя переносить картинку в неподходящий раздел только ради расстояния между изображениями;
- не делать отдельную картинку к каждому H2 автоматически и не копировать одну композицию с заменой подписей;
- таблица, список или формула сами по себе не являются местом для картинки. Иллюстрация ставится там только если раскрывает тот же смысл;
- поле `Место в статье` должно содержать точный H2 и точную точку вставки внутри раздела: после конкретного абзаца, списка, таблицы или формулы;
- точка вставки должна быть однозначной. Для абзаца указывать его короткую уникальную конечную фразу или другое понятное текстовое основание;
- нельзя оставлять формулировку только `после раздела`, если внутри раздела есть несколько возможных мест.

## 12.1. Технический SEO/GEO-чек

После подготовки статьи выполнить технический SEO/GEO-чек, если доступен опубликованный URL или тестовая страница. Если статья существует только как текст и страницы ещё нет, не имитировать техническую проверку и не придумывать её результаты.

Проверить:

- страница доступна поисковому роботу и не закрыта от индексации через `robots.txt`, `noindex` или другие ограничения;
- основной URL и `canonical` не создают конфликтов и не указывают без причины на другую страницу;
- основной текст статьи доступен как обычный индексируемый текст страницы, а не только внутри изображения, `canvas`, закрытого интерфейса или элемента, требующего действия пользователя;
- `seo_title`, `meta_description`, H1 и фактическое содержание страницы соответствуют друг другу и поисковому интенту;
- изображения имеют осмысленный `alt`, а важные факты и выводы из изображений продублированы обычным текстом;
- если на сайте используется Schema.org для статьи, разметка валидна, соответствует видимому содержанию страницы и не содержит придуманных сущностей, оценок, дат или других данных;
- нет технических причин, из-за которых основной контент страницы недоступен поисковым или генеративным системам.

Не добавлять специальные AI-блоки, скрытый текст, искусственные FAQ, отдельную «разметку для нейросетей», `llms.txt` или другие технические элементы только ради GEO, если для них нет самостоятельной подтверждённой задачи. GEO не заменяет обычную индексируемость и техническое SEO.

Технический чек не выводить отдельным блоком вместе со статьёй, если пользователь специально этого не просил. Если обнаружена критичная проблема существующей страницы, которая мешает индексации или корректному пониманию контента, кратко сообщить о ней до готового текста статьи.

## 13. Формат результата этапа 1

Выводить три технических раздела `SEO-META`, `ARTICLE-BODY`, `IMAGE-SPECS`, но для пользователя группировать их **в две независимо копируемые части**:

1. **Статья:** сначала `SEO-META`, затем полный `ARTICLE-BODY`.
2. **Задания для изображений:** после статьи один отдельный непрерывный копируемый блок, содержащий полный `<IMAGE-SPECS>` с заданиями от `IMAGE-SPEC-1` до `IMAGE-SPEC-N`.

**Главное требование к отображению:** пользователь должен иметь возможность скопировать **только весь IMAGE-SPECS одним нажатием**, без статьи и сопроводительного текста. Если невозможно отправить два отдельных сообщения в одном ходе чата, оформить `IMAGE-SPECS` самостоятельным блоком кода `text` с доступной кнопкой копирования. Не разбивать задания на отдельные блоки копирования, не прятать их внутри общей статьи и не смешивать с пояснениями. Не обещать отдельное сообщение, если интерфейс не позволяет его отправить автоматически.

До выдачи материалов кратко объяснить, что меняется и почему, когда задача касается обновления статьи. После выдачи полного текста статьи и отдельного копируемого `IMAGE-SPECS` остановиться. Не запускать иллюстрации в том же ответе. Каждую картинку создавать только по отдельной команде пользователя с указанием номера или с одним соответствующим `IMAGE-SPEC-N`. TXT и ZIP здесь не создавать: финальная сборка выполняется только по отдельной команде.

### SEO-META

```text
<SEO-META>
article_type: STANDARD или FORECAST
seo_title: ...
meta_description: ...
slug: ...
primary_query: ...
</SEO-META>
```

Этот блок является техническим. При публикации его значения помещаются в metadata и не выводятся читателю.

### ARTICLE-BODY

```text
<ARTICLE-BODY>
# H1

Готовый текст статьи...
</ARTICLE-BODY>
```

Внутри `ARTICLE-BODY` запрещены служебные метки `Title:`, `Description:`, `H1:`, `H2:`, `H3:`, план иллюстраций и технические комментарии.

### IMAGE-SPECS

После статьи сформировать **N самостоятельных заданий (`N >= 3`)**, где N выбран по смысловому обзору готовой статьи. Нумеровать без пропусков от `IMAGE-SPEC-1` до `IMAGE-SPEC-N`. **Весь блок ниже выдавать отдельно от статьи как единый копируемый фрагмент**:

```text
<IMAGE-SPECS>
## IMAGE-SPEC-1
Место в статье: точный H2 + точная точка вставки внутри раздела
Главная мысль: одна мысль
Сюжет: один сюжет
Визуальный тип: SCENE / PROCESS / COMPARISON / CALCULATION / SINGLE_OBJECT
Композиция: краткое описание компоновки
Главные объекты: конкретный список
Точный текст: один короткий заголовок и до пяти подписей длиной 1-3 слова каждая либо `Без текста`
Числа: точные значения или `Нет`
Alt: естественное описание
Подпись: короткий видимый текст под изображением

## IMAGE-SPEC-2
...

## IMAGE-SPEC-3
...

## IMAGE-SPEC-N
... (последнее задание, если N больше 3)
</IMAGE-SPECS>
```

Каждое задание должно иметь собственную главную мысль и выразительный сюжет. Сюжеты должны различаться содержанием, объектами или визуальной механикой. Нельзя создавать несколько вариантов одной схемы ради увеличения числа изображений.

Все поля `Место в статье` должны вести в разные обоснованные смысловые точки. Две картинки нельзя планировать подряд или после одного и того же блока. Число заданий фиксируется в конце этапа 1 и используется без изменений при генерации и сборке, если пользователь прямо не утвердил новый план.

`IMAGE-SPECS` являются техническим заданием и не включаются в публикуемый текст или финальный TXT. При финальной сборке из них используются только номер картинки, Alt, Подпись и точная точка вставки.

**Как запускается генерация:** полный `ARTICLE-BODY` и весь `IMAGE-SPECS` сами по себе не запускают изображения. Весь `IMAGE-SPECS` обязательно показать отдельно, единым копируемым блоком, чтобы пользователь мог выделить и прислать нужный `IMAGE-SPEC-N`. Каждое отдельное задание самодостаточно: пользователь присылает только его либо называет конкретный номер. Такая команда запускает только указанную картинку, после чего нужно остановиться. Повторная отправка всего плана без номера не запускает комплект. Ошибки и повторы обрабатывать по `instruktsiya-illyustratsii-v7.md`.

## 14. Финальная проверка

Перед выдачей проверить:

- определён тип `STANDARD` или `FORECAST`;
- закрыт основной интент;
- сразу после H1 есть прямой ответ на основной запрос;
- ключевые H2 начинаются с ответа по существу, если это соответствует их функции;
- важные смысловые блоки понятны без обязательного чтения соседних разделов;
- факты, расчёты, прогнозы и экспертные выводы не смешаны;
- нет искусственного дробления текста и FAQ ради GEO;
- нет воды, повторов и переспама;
- факты и изменяемые цифры проверены;
- если дорабатывается опубликованная страница, проанализирован весь значимый набор запросов URL, а не только основной запрос;
- если дорабатывается опубликованная страница, проверена каннибализация по приоритетным запросам;
- если дорабатывается опубликованная страница, актуальный топ Яндекса изучен именно по реальным точкам роста;
- если позиция хорошая, но CTR слабый, отдельно проверены Title и фактический сниппет до крупной переработки текста;
- после доработки опубликованной страницы проверена уместная внутренняя перелинковка на целевой URL;
- сильные части существующей страницы сохранены, если для их изменения нет обоснованной причины;
- не придуман личный опыт;
- есть добавленная практическая ценность;
- один H1 и логичная структура H2/H3;
- `seo_title` и `meta_description` уникальны и не шаблонны;
- внутренние URL существуют;
- данные иллюстраций присутствуют в тексте;
- выполнен смысловой обзор статьи и выбран обоснованный объём иллюстраций, не менее трёх;
- есть ровно N самостоятельных `IMAGE-SPEC` без пропусков в нумерации;
- у каждой картинки указаны точный H2 и однозначная точка вставки;
- у каждой картинки есть отдельные поля `Alt` и `Подпись`, которые не дублируют друг друга дословно;
- все картинки распределены по разным подходящим смысловым местам и не стоят подряд;
- не пропущены значимые возможности для визуального объяснения, нет декоративных дублей;
- технические блоки отделены от `ARTICLE-BODY`;
- весь `IMAGE-SPECS` находится в одном самостоятельно копируемом блоке, отдельно от статьи;
- если доступен опубликованный URL или тестовая страница, выполнен технический SEO/GEO-чек из раздела 12.1; если страницы ещё нет, техническая проверка не имитировалась.

После выдачи полного `SEO-META`, `ARTICLE-BODY` и отдельного `IMAGE-SPECS` остановиться. Ни одну картинку автоматически не запускать. Все `IMAGE-SPEC-1 ... IMAGE-SPEC-N` создаются только после отдельных команд пользователя. Архив и TXT создавать только по отдельному запросу после готовности всего комплекта.
