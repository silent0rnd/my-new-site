# Постоянная память и история SEO-решений

## Зачем

Память Codex между сессиями не должна полагаться на разговорный контекст.
Авторитетны файлы, версионируемые в репозитории, плюс текущие внешние источники.
Файл памяти фиксирует принятый вывод с источником и датой, а не заменяет
Яндекс Вебмастер, GSC, Bing, SEO-карту или Google-таблицу.

## Порядок установки и обнаружения

1. Найди в репозитории существующие заметки SEO, `AGENTS.md`, карту интентов,
   журнал усилений, файлы Webvisor, отчёты и проектный backlog.
2. Если файлы уже являются постоянным источником, **используй их**, не создавай
   параллельные реестры. Запиши пути/URL в кратком указателе `project-context.md`.
3. Если постоянных файлов состояния нет, создай `docs/seo/` из `memory-seed/`.
   Не копируй шаблоны поверх реальных записей и не меняй историю задним числом.
4. Для каждого факта сохраняй `дата, источник, URL/область, версия решения,
   статус уверенности`. Отмечай непроверенные/устаревшие сведения.
5. Не сохраняй ключи доступа, пароли, cookie, персональные данные, API-ответы
   с секретами. Файлы памяти разрешено коммитить только без чувствительных данных.

## Структура (если нет аналогичной)

- `docs/seo/project-context.md`: назначение процессов, ссылки и реальные пути
  к первичным источникам, критерии приоритетов и текущие договорённости.
- `docs/seo/decision-log.md`: **журнал решений**, а не журнал выполненных правок.
  Каждая запись содержит ID, дату, URL/кластер, источники, принятое решение,
  автора согласования, ссылку на задачу/commit, текущий статус, supersedes.
- `docs/seo/working-state.md`: открытые задачи с владельцем, следующим шагом,
  условием запуска, статусами `planned / waiting-data / approved / implemented /
  monitoring / closed / rejected`, ссылкой на решение.
- `docs/seo/source-registry.md`: источники, URL/пути, схема, даты обновления,
  статус доступа, права, известные ограничения. **Без** токенов и секретов.

## Единственный источник истории внедрения

Google-таблица `SEO мониторинг naklikay.ru` и её `Журнал усилений`, если
они доступны, остаются каноническим журналом реально внедрённых изменений.
Файловый `decision-log.md` описывает *почему выбрали решение*, в том числе
вариант `не менять`, но не создаёт вторую копию таблицы `Журнал усилений`.

Для утверждённой правки:
1. Запиши решение и baseline до изменения (при наличии первичных данных).
2. Внедряй только после разрешения, сохраняя изменение как diff/commit.
3. После проверки факта публикации занеси запись в канонический журнал.
4. Если доступа на запись нет, в `working-state.md` укажи
   `sync-pending` и подготовь точную запись, не утверждая, что обновил журнал.
5. Когда наступило сопоставимое окно, проверь фактический результат и закрой
   задачу или запиши новую гипотезу. Корреляция не доказывает причинность.

## Обновление и предотвращение расхождений

- Перед задачей прочитай только релевантные разделы памяти и актуальную таблицу;
  полный архив обсуждений не загружай каждый раз.
- Не изменяй принятое решение молча: добавь новую запись `supersedes: ...`.
- Не удаляй старые решения, сохраняй историю в Git/документе.
- Статус `implemented` только после фактического изменения файлов/сайта;
  `monitoring` только с известной датой и метриками baseline.
- При недоступной базе памяти покажи блокер, не имитируй восстановление.
- Перед обновлением файлов проверь на конфликт одновременных изменений; не
  перезаписывай чужие правки. Для массовой синхронизации нужна отдельная команда.

## Проверка качества памяти

В новой сессии агент должен ответить на вопросы без домыслов: (a) где свежие
данные; (b) какие URL сейчас наблюдаем; (c) что утверждено, но не внедрено;
(d) какие изменения были реально опубликованы; (e) что ещё не проверено.
Если какой-то ответ отсутствует в источниках, он должен быть `неизвестно`.
