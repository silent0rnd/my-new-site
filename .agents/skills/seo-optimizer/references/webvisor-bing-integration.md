# Задание на второй этап: интеграция Bing в Webvisor

**Статус:** проектный план, не команда на выполнение. На первом этапе
устанавливается `seo-optimizer`; текущие скрипты Webvisor и таблицы не трогать.

## Условия старта

- Найдены реальные исходники/версии сценариев Webvisor, назначение каждого,
  конфигурация расписания, источники Яндекса/GSC и место хранения данных.
- Сняты резервные копии текущих скриптов и схем таблиц, подтверждён baseline.
- Проверена официальная документация Bing REST API и реальные возможности
  доступа к выбранной property; токены находятся в защищённом хранилище.
- Пользователь отдельно разрешил реализацию и тестовый запуск Bing-адаптера.

## Дизайн интеграции

1. Не переписывать работающие Яндекс/Google-коннекторы. Сделать отдельный
   источник `bing_search` за общим адаптером, либо существующий механизм
   коннекторов, если он уже есть. Сначала read-only.
2. Разделить `bing_search` и `bing_ai_performance` как **разные датасеты**.
   Для AI выбрать поддерживаемый штатный экспорт или API, если официальный
   доступ подтвердится; иначе пометить `manual / unavailable`.
3. У каждого значения хранить `source, site_property, metric_name,
   value, time_start, time_end, date_extracted, granularity, filters,
   dimensions, source_ref, status`. При необходимости отдельные таблицы
   сырых ответов и нормализованных значений; не разрушать существующую схему.
4. Хранить признаки `complete / partial / delayed / unsupported / failed`,
   дату последней доступной записи. При первой неделе накопления не
   интерпретировать пропуски как ноль.
5. Идемпотентная загрузка: ключ строится из источника, site/property,
   периода, метрики, измерений и фильтров. Повторный запуск не создаёт дублей.
6. Технический отчёт по каждой загрузке: время, ошибки API, последние даты,
   записанные строки, дубликаты, покрытие, retries/rate-limit, метки частичной
   загрузки. Секреты исключить из логов.
7. Сверить тестовый период с числами интерфейса Bing при одинаковых фильтрах;
   не считать разницу ошибкой, не проверив задержку/агрегацию/округление.
8. Сначала shadow-период: данные Bing доступны отдельно, но не влияют на
   приоритеты и существующие Google/Яндекс отчёты. После проверки включить
   в SEO-анализ как **третий отдельный источник**.
9. При наличии реальных AI-метрик добавить их в существующую систему
   под отдельной сущностью/типом источника, без искусственного среднего KPI.
10. Ввести контрольная проверка: обновление после сбоя, пустой ответ,
    частичный период, duplicate fetch, rate limit, недоступный токен,
    несовпадение host/path, корректное восстановление без потери истории.

## Что агент должен предъявить перед изменением скриптов

- список обнаруженных скриптов и триггеров, источников и таблиц;
- различие текущей схемы с проектной;
- проверенную таблицу методов Bing REST API, реально доступных полей;
- точный diff изменений и план отката;
- набор тестов и результаты контрольной выгрузки;
- риски прав доступа и нарушения старого мониторинга.

Ни один API endpoint, авторизационный параметр, число полей или лимит не
следует придумывать до проверки документации и реального метода.
