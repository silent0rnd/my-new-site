# Данные и источники правды

## Приоритет источников

1. Фактический публичный сайт (доступность URL, код ответа, canonical, sitemap, внутренние ссылки) и текущий репозиторий - для того, что действительно опубликовано.
2. Актуальная Google-таблица `SEO мониторинг naklikay.ru` и её журнал изменений - для аналитики и исторических SEO-решений. Приоритет фактической свежести выше «даты создания отчёта».
3. Живые/экспортированные данные Яндекс Вебмастера по URL и запросам; PRO URL+query+region при наличии. Использовать доступный API/экспорт, не требовать исключительно PRO.
4. Отдельная таблица Google Search Console - дополнительный независимый источник. Не соединять показатели разных систем в один CTR или «общую среднюю позицию».
5. Bing Webmaster Tools - отдельный источник поисковых показателей и индексирования. Отчёт AI Performance учитывать только как самостоятельный, подтверждённый тип данных, не смешивая его с обычным поиском. Подробнее: `bing-webmaster.md`.
6. Яндекс Метрика - для органических визитов и бизнес-эффекта, только при подтверждённой корректности выгрузки.
7. Актуальная SEO-карта интентов, поисковая выдача, официальный справочник Яндекса для изменяемых функций/технических вопросов.

## Листы мониторинга

| Лист | Что извлекать |
|---|---|
| Журнал усилений | дата изменения, URL, тип правки, статус, период наблюдения; исключение недавних повторных улучшений |
| Страницы | показы, клики, CTR, средняя позиция за последние 7 и 28 дней и сравнимые окна |
| Запросы | фактический запрос, целевой URL, показы, клики, позиция, интент; приоритет по кластеру |
| История страниц | подтверждённый тренд, полнота дат, выпадения, давность страницы |
| Проблемы | индексирование, технические статусы, ошибки, рекомендации |
| Метрика | органические визиты, если источник живой и интервал корректен; пустота != ноль |
| Фразы | контрольная семантика, соответствие группам, не полная семантика по умолчанию |
| Реестр URL | актуальность/назначение URL, сверка с sitemap и сайтом, не доказательство индексации |

Названия листов основаны на рабочих материалах проектов. Фактическую схему данных нужно проверить при каждом подключении. Если листа нет или столбцы переименованы, не подставлять догадки.

## Надёжность периодов

В каждом отчёте фиксировать: источник, дату получения, дату максимальной доступной записи, временную зону (если известно), окно дат, полноту, уровень гранулярности (день/URL/запрос/регион), ограничения и ссылку на исходник.

- Неделя = ровно 7 дней. Сравнение с предыдущей неделей только для одинаково полных окон.
- Окно 28 дней = 28 дней; сравнение с предыдущим сопоставимым окном, когда доступно.
- Сравнивая 7 и 28 дней, нормализовать суммы на дни и не делать вид, что окна независимы при перекрытии.
- Позиция по запросу может зависеть от выбранной методики агрегации/гео, не усреднять простым средним средние из несовместимых уровней отчётности.
- `CTR = клики / показы × 100%`, если это одни и те же база, период, поисковая система и сегментация.
- Одни и те же показы, повторённые в экспортированных строках на разных уровнях детализации, нельзя повторно суммировать.
- Низкое число показов не позволяет уверенно оценить CTR или эффект SEO-правки. Не вводить произвольный «универсальный порог значимости».

## Историческое ограничение, не текущий диагноз

В октябре - начале ноября 2026 обычный сбор Яндекса в сценарии `seo_webmaster_weekly_audit_v3_11.gs` работал, но PRO `/pro/serp/dates` имел сбой на уровне `UrlFetchApp.fetch()`; URL-привязанные обычные данные были неполными или устаревшими. Это прошлое наблюдение, **не утверждение о статусе сервиса сейчас**. При новой проверке самостоятельно перепроверить доступ и свежесть, не менять скрипт наугад.

## Нет доступа

Если таблица, API или файлы недоступны: перечислить недоступные источники, что проверено вместо них, какие выводы надёжны, какие остаются гипотезами, и что нельзя делать до данных. Не сообщать якобы свежие показатели.
