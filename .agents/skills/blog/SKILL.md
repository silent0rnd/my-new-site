# Статьи блога Naklikay

Сначала выбери сценарий: **A - новая статья; B - существующая статья**. Не выполняй A при B. Утверждённые текст, SEO и изображения сохраняй: качество важнее экономии действий. Следуй `AGENTS.md`.

## Экономный процесс
1. До чтения файлов классифицируй задачу: новая статья, полная замена, текст абзацев, SEO, H1/карточка, H2/H3, изображения или вёрстка. Выполняй только нужную ветку.
2. Не используй построчный вывод (`rg -n`, `Select-String`) для совпадений внутри минифицированного HTML: одна строка может содержать всю статью. Извлекай только значения, счётчики или ограниченный фрагмент до 300 символов.
3. Не выводи утверждённый текст целиком. Для полной замены передавай TXT штатному преобразователю, для точечной правки извлекай только метаданные, заголовки и изменяемые фрагменты.
4. Перед записью собери в один проход все зависимые изменения целевой страницы: title/description, OG, Twitter, JSON-LD, даты, canonical, главное изображение и карточку. После этого выполняй синхронизацию и сборку.
5. Используй `build:blog -- --article <slug>` для одной статьи. Полную сборку запускай только после изменения генератора, общей логики или когда целевой режим не поддерживает необходимый контракт.
6. В существующей статье оптимизируй только добавленные или заменённые изображения через повторяемый `--image`; старые изображения не переэкспортируй.
7. После штатных тестов выполни один объединённый валидатор текста, файлов, SEO, структуры, ссылок, изображений и артефактов. Успешные факты повторно не проверяй.
8. Браузер запускай только при визуальных изменениях и проверяй desktop, mobile, lazy-изображения, переполнение и консоль в одной сессии. Если для Playwright заранее известно требование разрешения среды, запроси его при первом запуске без заведомо заблокированной попытки.
9. Скриншоты делай только при ошибке или нестандартном визуальном решении.
10. Для новой статьи используй шаблоны и до вёрстки прочитай только релевантные проверки `tests/blog-article-target.test.js` для применяемых конструкций.
11. Проверяй только добавленные или изменённые внутренние ссылки; полный обход выполняй только по обязательному контракту новой статьи.
12. Преобразуй утверждённый исходник в HTML одним детерминированным проходом. До записи сверь количества элементов с исходником; не передавай полный HTML между командами и не собирай его по фрагментам.

## Общее
- Работай только с целевыми файлами. Для новой статьи изучи один актуальный образец, для существующей - HTML в объёме задачи. При точечной замене найди одно совпадение и изучи его раздел; весь HTML читай при полной или структурной правке. Не проводи аудит сайта и не меняй общие стили, скрипты или архитектуру.
- Внешние ссылки не добавляй. В новую или полностью заменяемую статью добавляй 2-4 проверенные внутренние ссылки с осмысленными анкорами и новой вкладкой. Весь блог не сканируй; при точечной правке ссылки без запроса не добавляй.
- Списки оформляй `<ul>/<ol><li>`, не абзацами с дефисами; служебные `Title:`, `H1:` и др. не выводи в тексте. В изменяемом тексте ставь `&nbsp;` в многозначных числах, суммах и единицах (`36&nbsp;000&nbsp;₽`), `&#8209;` - в диапазонах (`10&#8209;15&nbsp;заявок`).
- Сохраняй `.article-lead`. В новой или полностью обновляемой длинной статье выделяй 1-3 вывода через `<p class="content-key-point">`. «Коротко» оформляй как `<aside class="content-key-point">` с `<p>` и `<ul><li>` после вступления, до TOC. Стиль: оранжевая линия без фона и рамки, 25-31 px desktop, 24 px mobile. Не включай блок в TOC и не применяй акцент к FAQ, формулам и обычным абзацам.

## A. Новая статья
1. По шаблонам из `templates/` создай `blog/<slug>/index.html` и карточку в `blog/index.html`. Замени все `{{PLACEHOLDER}}`; служебные маркеры публиковать нельзя. Сохрани оболочку, стили и скрипты; другие статьи вручную не меняй.
2. Добавь один H1 и логичные H2/H3; SEO title/description, self-canonical, `index,follow`, Open Graph, favicon `/assets/avatar-donut.svg?v=2`, `BlogPosting` или `Article` JSON-LD, `BreadcrumbList`, реальные автора и дату. Подключи URL к sitemap штатным механизмом.
3. После текста добавь видимый `.article-author`: `../../assets/author-avatar.jpg`, Максим Мирошников, «Специалист по платному трафику и Яндекс Директу», текст о 10-летнем опыте и `../../#about` («Подробнее обо мне»). Сохрани автора в JSON-LD.
4. Вставь только переданные изображения. Для новой статьи один раз запусти `npm.cmd run optimize:blog-images -- --article <slug>` (WebP 640/1080/1720 px, без увеличения). Оригиналы сохрани.
5. Один раз запусти `npm.cmd run build:blog -- --article <slug>`: он обновляет архив, добавляет целевой URL в sitemap, обновляет TOC, `.related-articles` и `scripts/blog-related-topics.json`. Сгенерированное вручную не правь; изменения связанных страниц допустимы.
6. Один раз выполни `npm.cmd run test:blog-article -- --article <slug>` и `npm.cmd run test:related-articles -- --article <slug>`. Полный `test:related-articles` запускай только после изменения генератора, алгоритма рекомендаций, общих стилей или скриптов блока.
7. `test:blog-toc`, `test:favicon`, `test:blog-images` запускай только при локальной проблеме или изменении проверяемого механизма. Полного аудита не делай.

## B. Редактирование существующей статьи
1. Изучи целевой `blog/<slug>/index.html` и указанные материалы. URL, неизменённые элементы и другие страницы не трогай.
2. **Полная замена из готового TXT с `<SEO-META>` и `<ARTICLE-BODY>`:** не собирай HTML вручную и не печатай его в контекст. Сначала запусти проверку `npm.cmd run update:blog-article -- --article <slug> --source <txt> --image <путь>`; каждый переданный файл добавляй отдельным `--image`. Команда обязана проверить slug, структуру, число заголовков и картинок, конфликт имён файлов и размеры, но ничего не записать. Только после успешного результата повтори ту же команду с `--write`.
3. После полной замены одним ограниченным извлечением проверь согласованность title/description, OG, Twitter, JSON-LD, canonical, дат и главного изображения. Исправь найденные расхождения одним патчем, затем при изменении H1, description или главного изображения выполни `sync:blog-card` в режиме проверки и с `--write`.
4. Для заменённых изображений один раз выполни `optimize:blog-images` со всеми именами из результата преобразователя, затем один раз `npm.cmd run build:blog -- --article <slug>`. После сборки запусти один `npm.cmd run test:blog-refresh -- --article <slug> --source <txt>`; удалённые старые изображения передавай повторяемым `--old-image`. При изменении изображений, таблиц или вёрстки дополнительно один раз запусти `npm.cmd run test:blog-refresh:visual -- --article <slug>`. Скриншоты нужны только при ошибке или нестандартном визуальном решении.
5. **Только текст абзацев:** потребуй одно совпадение исходного фрагмента; после замены проверь отсутствие старого и наличие нового. Если H2/H3, метаданные и изображения прежние, не запускай сборку, оптимизатор, глобальные тесты, браузер, sitemap и проверку чужих карточек.
6. **H2/H3:** один раз запусти `npm.cmd run build:blog -- --article <slug>`, проверь заголовки и ссылки TOC целевой статьи. Общий аудит не запускай.
7. **Только SEO `<title>`, description или `dateModified`:** синхронизируй SEO-поля целевой статьи. При прежних H1 и карточке сборка не нужна.
8. **Публичный H1/название или данные карточки:** синхронизируй карточку, если пользователь не требует сохранить её прежней; обнови зависящие SEO-поля и один раз запусти `npm.cmd run build:blog -- --article <slug>`. Проверь затронутые карточки и рекомендации; весь архив и общий тест без конкретной ошибки не проверяй. `lastmod` чужих URL не меняй.
9. **Изображения не менялись:** не создавай WebP, не запускай оптимизатор или тесты изображений и не меняй `src`, `srcset`, alt, размеры и имена файлов.
10. **Изображения добавлены или заменены:** один раз запусти `npm.cmd run optimize:blog-images -- --article <slug> --image <имя или src>`; для нескольких файлов повтори `--image` в той же команде. Проверь `<picture>` только у выбранных изображений и неизменность старых фигур. Рекомендации обновляй только по запросу или при изменении карточки; сгенерированное вручную не правь.

## Изображения и проверка
- Новые изображения считай дополнением, если замена не указана прямо. Не придумывай иллюстрации; проверь число переданных, сохранённых и добавленных файлов. При замене удаляй старые ссылки и файлы только после проверки их использования.
- Утверждённые локальные изображения с указанными путями не открывай для визуального анализа, если пользователь не просит сравнить дизайн, найти дефекты, перерисовать или отредактировать их. Для обычной публикации проверяй имена, количество, размеры, пропорции и при необходимости хеши без вывода изображений в контекст.
- Перед генерацией или перерисовкой изучи бриф, исходники и дизайн-систему. До заявления о соответствии сравни с ними сюжет, текст, цвета, пропорции, размеры и дефекты результата.
- Для иллюстраций используй `<picture>`: WebP `srcset`, `sizes="(max-width: 720px) calc(100vw - 36px), 860px"`, исходный JPG/PNG в `<img src>`. Сохрани alt, width/height и пропорции. Изображение первого экрана не делай lazy; ниже используй `loading="lazy"` и `decoding="async"`. Не обрабатывай старые изображения без запроса, логотипы, автора и похожие статьи.
- Проверяй затронутый контракт: H1, ссылки, изменённые метаданные, HTML, изображения и артефакты `�`, `undefined`, плейсхолдеры. Успешное не перепроверяй. Браузер desktop/mobile нужен при изменении вёрстки, стилей, изображений или визуальном риске. Выполняй одну сессию: desktop, mobile, прокрутка lazy-изображений, переполнение, размеры изображений, таблицы и консоль. Скриншот делай только при проблеме или нестандартном визуальном решении.
- Несвязанную ошибку общего теста не исправляй. Если необходимая сборка изменила другие страницы, перечисли реальные изменения.
